# 澄清问题 · Issue #15

> 基于 2026-08-18 提供的 G2B/B2B Agent 交流广场场景描述，向人类 PM 提出以下澄清问题。这些问题按 Johari 象限组织，旨在暴露假设、明确边界、降低后续设计与实现风险。

---

## 一、知道自己知道（请确认我们的理解是否正确）

1. **范围确认**：本期 Issue-15 的核心目标是否是先跑通「企业 agent 在 Town Square 发布供需 → 匹配 → 建群 → 交换信息 → HITL 确认 → 生成订单」这一个闭环，而不是同时做政府审批、支付、物流履约？
2. **技术底座确认**：是否继续沿用 Issue-14 确定的 OpenClaw + Mattermost + Teable 组合，不再引入新的 agent 框架或 IM/表格系统？
3. **HITL 原则确认**：是否沿用 Issue-14 的硬规则——生成订单/协议前必须得到双方人类成员显式确认，agent 不能擅自成交？

## 二、知道自己不知道（需要 PM 给出方向）

4. **供需信息发布模板**：一条供需话题必须包含哪些字段？例如：标题、类型（供给/需求）、行业、数量、交付时间、地理位置、预算区间、联系方式可见性？
5. **意向判断机制**：agent 如何判断是否匹配？是基于可配置规则（关键词、标签、地理位置），还是由 LLM 自由推理？是否需要人类预设匹配阈值？
6. **建群权限**：是否任何企业 agent 发现匹配后都可以直接拉群？还是必须先获得本企业人类成员的授权，或在配置白名单内才能建群？
7. **私密频道信息边界**：公共广场只展示哪些信息？价格、联系方式、企业资质等敏感字段是否只在私密频道展示？人类成员能否设置「哪些信息可对哪些企业可见」？
8. **订单定义**：人类确认后生成的「订单」是什么形态？是 Teable 中的一条记录、一份 PDF 合作意向书、还是一个带状态的工单？是否需要编号、签名、审批流？
9. **政府角色位置**：G2B 场景下，政府部门是只作为广场上的「企业」参与供需，还是作为平台监管/审批方存在？是否需要专门的监管 agent 或运营视图？

## 三、不知道自己不知道（请 PM 举具体例子帮助挖掘）

10. **请举一个完整案例**：例如「政府某局需要 1000 套物联网传感器，某制造企业可供应」，从发布到成单，双方人类成员分别在哪些节点收到通知、需要做什么决策？这个案例将作为演示剧本的主线。
11. **异常分支**：
    - 如果双方 agent 交换信息后，发现条件不匹配，流程如何结束？是否通知双方人类成员？
    - 如果一方人类成员长期不确认，是否有超时提醒或自动驳回？
    - 如果多家企业 agent 同时对同一条供需有意向，是先到先得、多方比价，还是全部拉入一个群？
12. **隐私与合规**：不同企业之间是否天然互信？是否存在竞对关系导致的信息隔离需求？是否需要「黑名单」或「仅对认证企业可见」的机制？
13. **度量和成功标准**：如何衡量 Agent 交流广场的效果？是撮合成功率、成单金额、响应时长，还是 agent 自主完成率？

## 四、落地优先级

14. 在以下可能的 MVP 范围中，哪一项应优先交付？
    - A. 先做一个最小闭环：只支持「供给」发布，匹配后由人类手动确认是否建群，agent 只负责发布与推荐。
    - B. 半自动闭环：agent 自动匹配并建群，但方案草拟与订单生成由人类主导。
    - C. 全自动闭环：agent 完成发布、匹配、建群、信息交换、方案草拟，人类只在最终确认节点介入。
15. 前端/UI 开发希望拿到的大纲粒度是什么？是否需要包含页面地图、信息架构、组件列表、交互规则、异常分支，还是只需要关键页面草图和演示剧本？
