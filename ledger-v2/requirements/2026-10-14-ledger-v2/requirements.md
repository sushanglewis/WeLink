# 需求文档：龙小督台账 V2

<!-- status: approved -->

## 背景

- 需求来源：六份 REQ 附件、本轮产品澄清、线上只读观察。
- 访谈摘要：`ledger-v2/interviews/2026-10-14-ledger-v2/summary.md`
- 外部跟踪：产品经理手工录入 Gitee；本工作包不创建 GitHub Issue。
- 线上现状：台账按批次展示跟进记录，批次使用长数字编号，事项详情缺少独立「交办内容」，提交后上游在现有节点继续处理。

## 问题

1. 经办人只能看到标题级「交办事项」，无法在填报现场理解具体工作要求。
2. 错误下发后不能撤回，且错误记录仍影响 72 小时重复督办判断。
3. 批次名称不可读，同一截止时间的批次无法快速区分。
4. 被拆分导入的逻辑批次需要逐个导出并人工合表。
5. 单选批次使用户必须逐批寻找事项，导出弹窗又与台账处理现场割裂。
6. 下游提交质量不合格时，上游只能继续提交，无法退回修改。

## 用户

- **督办人**：发起批次、最终把关、撤回误下发事项、导出结果。
- **经办人**：接收督办，直接填报或转办；审核转办人的提交。
- **转办人**：填报或再次转办；审核次级转办人的提交。
- **次级转办人**：链路末端填报者。
- 同一账号可在不同事项中兼任多个角色，权限按“批次跟进记录 × 当前节点”判断。

## 统一流程原则

### 提交即认可并上报

下游提交后，上游收到龙小督通知与台账待办，并看到最新填报版本。上游在现有「待××提交」节点只有两个业务决策：

- **提交**：认可当前内容；允许在提交前做必要修订；保存新版本并直接上报更高一级。
- **打回**：不认可当前内容；原因必填，退回实际直接下游重新填报。

不新增「待审核」「审核通过」等中间状态，不设置独立「通过」按钮。（来源：讨论纪要 00:10:00—00:36:00）

督办人为最终节点，有两种认可路径：

- **逐项认可**：督办人润色或修改当前事项后点击提交；事项跟进状态改为「已审核」，事项节点状态改为「督办人已审核」。
- **批次认可**：督办人不逐项提交，直接导出符合条件的批次；导出即表示认可该批次全部有效填报内容，并统一归档。

### 直接下游判定

- `待转办人提交`：直接下游为次级转办人。
- `待经办人提交`：直接下游为转办人。
- `待督办人提交`：直接下游为经办人。
- 链路中不存在的角色直接跳过；系统以最近一次有效提交版本的作者和实际责任链为准，不按固定层级猜测。

## 功能需求

### REQ-01 交办内容展示

- 事项详情在「交办事项」下展示只读「交办内容」。
- 督办人、经办人、转办人、次级转办人均可见。
- 超过三行默认收起，支持展开/收起；空值显示「暂无交办内容」。
- 展示内容必须与督办人下发事项时填写的交办内容一致。
- Excel 字段规范已有独立口径，本迭代不重复定义。

### REQ-02 督办人撤回

- 仅发起该批次的督办人可撤回；仅允许撤回尚未导出归档的跟进记录。
- 撤回必须精确到“某一批次下的某一条事项填报记录”，不能影响其他批次中的同编号事项；事项编号只用于重复督办规则判断。
- 撤回原因必填，提交前二次确认。
- 成功后记录进入「已撤回」终态：下游表单与操作锁定、从待办移除，并由龙小督通知所有受影响协作者。
- 审计保留操作者、原因、时间、撤回前节点和版本；台账不新增冗余留痕横条。
- 72 小时去重忽略已撤回记录；重新下发后以新记录重新开始计时。
- 已撤回记录不参与导出完成性校验；批次不存在有效事项时不可导出。

### REQ-03 批次命名

- 展示格式：`YYYY-MM-DD HH:mm-N`。所有批次都必须带自增序号；同一截止分钟按创建先后显示为 `-1`、`-2`、`-3`。
- 时区固定为 Asia/Shanghai，截止时间规范化到分钟。
- 未提供截止时间时，以正式下发时刻 +36 小时生成截止时间。
- 序号按进入该截止分钟分组的顺序稳定分配，不因撤回或删除重排。
- 批次选择器、事项标签、通知引用及文件名统一使用展示名；内部批次 ID 不变。
- 历史批次必须先补齐截止分钟，再全量迁移展示名。

### REQ-04 多批次合并导出

- 批次选择框支持多选，当前选择范围同时决定下方事项卡合集和 Excel 导出范围。
- 用户进入台账时默认全选全部未归档批次；已归档批次默认不选中，但可手动选择回看。
- 批次选择提供「全选未归档」「仅选可导出」「清空」。
- 合并导出生成一个 Excel、单 Sheet；沿用既有导出字段规范。
- 批次内所有有效事项的「事项跟进状态」均属于「已填报」或「已审核」时可导出；不要求督办人逐项提交。
- 只要任一选中批次不满足条件或已经归档，整体禁止导出；系统不自动忽略，也不部分导出。
- 导出即批次级认可：下载成功后，该批全部有效记录的事项跟进状态统一改为「已归档」，事项节点状态统一改为「归档」。
- 每个批次展示总事项数、已撤回数、已填报数、已审核数、已归档数和待处理数；总事项数包含已撤回事项。
- 导出弹窗只确认当前选择范围、实际导出数量和归档影响，不再选择批次。
- 已撤回事项不参与校验，也不进入导出结果。
- 导出成功后，已归档批次自动取消选择，页面重新全选剩余未归档批次。

### REQ-05 统一台账视图

- 取消「按批次 / 平铺模式」切换，只保留批次多选控制的统一台账视图。
- 下方展示全部选中批次的事项合集，包括已撤回事项；事项卡显示所属批次。
- 按事项跟进状态优先级排序：逾期未填报 > 跟进中 > 已填报 > 已审核 > 已归档；已撤回记录排在已归档之后。
- 同一状态内再按填报截止时间升序；截止时间相同时按批次创建时间、事项编号稳定排序。
- 事项卡保持单行横向排列，不换行；用户可左右拖动浏览，也可使用左右切换按钮逐项切换。
- 卡片展示事项编号、交办事项、状态、批次展示名和截止时间。
- 没有未归档批次时默认不选中任何批次，并允许用户从批次列表选择历史记录查看。

### REQ-06 打回

- 当前角色在「待××提交」节点可打回直接下游；当前角色收到上游打回后，如果责任链中仍有自己的直接下游，也可继续向下打回。
- 打回原因必填；弹窗展示事项、提交人、当前内容摘要、退回对象、原截止时间与影响说明。
- 成功后节点退回直接下游处理节点，下游待办 +1，上游当前待办移除；龙小督向下游发送原因、事项和截止时间。
- 原内容保留为可编辑草稿；每次提交保存不可变版本，打回事件关联被打回版本。
- 重新提交后回到同一上游节点，可重复打回，不限次数。
- 连续向下打回时，每一级都必须重新填写打回原因，并分别形成流转记录和待办转移。
- 打回不修改批次截止时间；超过原截止时间时继续按「逾期未填报」处理。
- 「已退回」是事项跟进状态的新增值：打回使已填报置为已退回，任一下游协作者重新提交后回已填报；超过填报截止时间仍未重新提交转逾期未填报。
- 归档、已撤回、处理节点已经变化或操作人不是当前处理人的打回必须拒绝。

### 两套状态机

**事项跟进状态**显示在事项卡右上角，值集固定为：

1. 跟进中
2. 已填报
3. 已审核
4. 已归档
5. 逾期未填报

其中原「推进中」统一更名为「跟进中」。任一下游首次有效提交后进入「已填报」；督办人逐项提交后进入「已审核」；批次导出成功后进入「已归档」。

**事项节点状态**显示在事项卡左下角，值集固定为：

1. 待经办人处理
2. 待转办人处理
3. 待次转人处理
4. 待转办人提交
5. 待经办人提交
6. 待督办人提交
7. 督办人已审核
8. 归档

撤回不扩充上述两个枚举；系统使用独立「已撤回」生命周期标记覆盖卡片展示，并保留撤回前两项状态用于审计。

## 验收标准

- [ ] 六项功能在同一台账原型中可联动演示。
- [ ] 上游提交直接上报，打回直接退回实际下游，不出现额外审核步骤。
- [ ] 打回原因、版本、节点、通知和待办数量同步变化，重复打回可追溯。
- [ ] 批内有效事项均为已填报/已审核即可导出；督办人可逐项审核，也可直接用导出完成批次级认可。
- [ ] 导出成功后，批内有效记录的事项跟进状态均为已归档、事项节点状态均为归档。
- [ ] 批次多选、默认全选未归档、事项合集排序、批次命名与同截止序号符合规则。
- [ ] 交办内容长文本折叠正常，空值有明确提示。
- [ ] 无评论、评论数量或未读协作消息相关入口。
