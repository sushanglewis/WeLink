# Design Review：龙小督台账 V2

<!-- status: approved -->

## 背景

- 关联需求：`ledger-v2/requirements/2026-10-14-ledger-v2/requirements.md`
- 关联输入：`ledger-v2/interviews/2026-10-14-ledger-v2/summary.md`
- 现状证据：`.context/current-system-panel.png`

线上台账已经具备批次、事项卡、协作者、五要素表单、转办、提交和单批次导出。本次不重做产品骨架，而是在现有节点链上补充纠错能力、任务优先入口和批次效率能力。

## 设计目标

1. 让经办人打开台账即可理解并处理最紧急的事项。
2. 保持“提交即认可并上报”，用最少的新状态完成逐级打回。
3. 让错误下发可撤回、过程可审计、历史版本不可覆盖。
4. 让批次可读、可区分，并支持拆分批次一次合并导出。
5. 用一个可交互原型证明六项需求能在同一信息架构内协同工作。

## 范围

### 范围内

- 交办内容、撤回、批次展示名、批次多选与合并导出、统一台账视图、打回。
- 提交/打回版本与流转事件展示。
- 龙小督通知和待办数量的交互反馈。
- 四类角色及无转办/一级转办/二级转办链路。

### 范围外

- 评论、评论数、未读协作消息。
- 手动刷新。
- 真实系统改造、真实 Excel 生成、真实消息发送。
- 新建独立审批步骤或“通过”按钮。

## 关键决策

| 决策 | 采用方案 | 理由 |
|---|---|---|
| 审核语义 | 提交即认可并上报 | 延续线上心智，避免“通过后再提交”双重操作 |
| 打回建模 | 现有待上游提交节点的反向分支 | 不新增审核状态，仍能明确责任与待办归属 |
| 打回状态 | 流程事件 + 卡片提示 | 避免与跟进中/逾期未填报互斥冲突 |
| 历史内容 | 不可变提交版本 + 当前可编辑副本 | 兼顾重填效率与审计 |
| 督办终审 | 逐项提交或直接导出 | 小批次可逐项润色，大批次以导出作为批次级认可 |
| 导出资格 | 有效事项跟进状态均为已填报/已审核 | 兼容未逐项审核、部分逐项审核和全部逐项审核三种批次 |
| 撤回边界 | 归档前、原督办人、原因必填 | 已流出的 Excel 无法追回，归档后保持不可变 |
| 台账范围 | 默认全选全部未归档批次 | 批次多选同时决定事项合集和导出范围，消除弹窗跳转断点 |
| 已归档批次 | 默认不选中、可手动回看 | 保持默认工作区聚焦未归档事项，避免阻塞导出 |
| 导出阻塞 | 任一选中批次不合格则整体禁止 | 保证当前选择范围与实际导出范围完全一致 |
| 批次序号 | 同截止分钟稳定分配、不重排 | 保持通知、截图和历史引用稳定 |

## 打回操作契约

1. 待上游提交节点可以打回直接下游；收到上游打回后，如当前角色仍有下游，也可以继续向下打回。
2. 操作人必须是当前节点处理人；若事项状态或处理人已经变化，本次打回不再生效。
3. 弹窗只提交打回原因；未提交的上游表单修改不写入历史。
4. 成功后创建打回事件，引用最近一次提交版本，并将该版本作者作为直接下游接收人。
5. 当前表单复制最近提交版本供下游修改；历史版本保持只读。
6. 待办归属从上游原子转给下游；龙小督通知通过可靠事件发送。
7. 下游可重新提交，也可在仍有下游时继续向下打回；每一级动作独立留痕。

## 督办人终审契约

1. 在 `待督办人提交` 节点，督办人可修改/润色并逐项提交。
2. 逐项提交后，事项跟进状态由「已填报」变为「已审核」，事项节点状态变为「督办人已审核」。
3. 督办人无需逐项提交；当批次全部有效事项的跟进状态属于「已填报/已审核」时，可直接导出。
4. 导出表示对所选批次全部有效内容的最终认可；下载成功后跟进状态统一为「已归档」，节点状态统一为「归档」。
5. 导出资格只看事项跟进状态，不要求所有节点都为「督办人已审核」。

## 页面信息架构

- 顶部：台账标题、批次多选、当前用户待办数、选择范围摘要和导出入口。
- 统一事项区：展示所选批次的事项合集，先按状态优先级、再按截止时间排序；卡片单行横向排列，可拖动或用左右按钮切换。
- 事项详情：交办事项、交办内容、协作者、最新打回提示、五要素表单、流转记录。
- 固定操作栏：根据节点显示暂存、转办、打回、提交；禁用状态附原因。
- 弹窗：打回、撤回、导出最终确认；导出弹窗不再选择批次。

## 验收标准

- [ ] 三种责任链都能完成提交、打回、重填、再次提交，并进入已填报或已审核。
- [ ] 督办人逐项提交产生已审核/督办人已审核，也可不逐项提交直接导出合格批次。
- [ ] 每次提交产生新版本，每次打回关联正确版本与直接下游。
- [ ] 打回不新增审核节点，不改变批次截止时间。
- [ ] 已填报/已审核混合批次可导出，导出后两套状态统一归档。
- [ ] 撤回、打回、批次多选、命名和导出在同一业务结构中无冲突。
- [ ] 原型在批次选择变化后保持事项、计数和导出资格一致。
