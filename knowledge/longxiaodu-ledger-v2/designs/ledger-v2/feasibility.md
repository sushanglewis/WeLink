# 业务可行性分析：龙小督台账 V2

> 本文只评估业务规则是否完整、可执行和可验收。

## 业务可行性结论

本次六项需求可以在现有“批次—事项填报记录—逐级协作者”业务结构中成立：

- 打回复用现有待上游提交节点，不增加独立审批步骤。
- 督办人既可逐项修改和审核，也可用批次导出完成整批认可。
- 撤回与打回职责不同：撤回用于终止错误下发，打回用于要求直接下游修改内容。
- 批次多选把事项查看范围和导出范围统一在同一个台账现场，避免从导出弹窗跳回台账的场景中断。
- 默认全选未归档批次，使用户无需逐批寻找事项；已归档批次按需回看。
- 批次展示名只改变用户识别方式，不改变历史批次与事项关系。

## 业务前提

### 历史批次数据完整

- 历史批次必须补齐精确到分钟的填报截止时间。
- 无法确认截止时间的批次不能纳入统一重命名结果。
- 同截止时间批次的先后顺序需要有明确、稳定的业务依据。

### 责任链明确

- 每条记录必须明确督办人、经办人，以及实际存在的转办人和次转人。
- 打回只退给当前角色的实际直接下游；收到打回的角色如果仍有下游，可继续向下打回。
- 角色空缺时直接跳过，不创建虚假的待处理节点。

### 终审与导出口径统一

- 下游首次有效提交后为「已填报」。
- 督办人逐项提交后为「已审核」。
- 已填报和已审核都代表内容已经具备批次导出资格。
- 导出代表督办人对整批内容的最终认可，并关闭本轮记录。

## 业务风险与处理口径

| 业务风险 | 可能影响 | 业务处理口径 |
|---|---|---|
| 上游查看期间下游状态已变化 | 误打回或重复提交 | 只接受当前节点处理人的最新操作；状态变化后提示重新查看 |
| 龙小督通知延迟 | 下游未及时获知打回 | 台账待办和红色打回提示为准，通知作为主动提醒 |
| 历史截止时间缺失 | 批次名无法可信展示 | 先完成数据补齐，再进行全量切换 |
| 同一事项存在多个批次 | 撤回错误记录 | 操作界面必须同时说明所属批次和具体事项填报记录 |
| 督办人误以为必须逐项审核 | 大批次操作成本过高 | 导出入口明确说明“导出即认可并归档” |
| 已填报与已审核混合 | 用户误判是否可导出 | 批次摘要直接显示两类数量并给出可导出结论 |
| 默认全选包含不可导出批次 | 导出按钮暂不可用 | 标明阻塞批次及待处理数，并提供「仅选可导出」快捷操作 |
| 总事项数与导出数不一致 | 用户误认为数据遗漏 | 总事项数包含已撤回事项，同时单列已撤回数和实际导出数 |
| 打回发生在截止时间之后 | 下游无剩余整改时间 | 保持原截止时间并标记逾期，由业务人员自行判断处理优先级 |

## 业务准备清单

- [ ] 明确历史批次截止时间补齐负责人和完成标准。
- [ ] 确认现有事项责任链数据能够识别实际直接下游。
- [ ] 确认龙小督提交、打回、撤回、导出通知文案。
- [ ] 确认批次多选对总数、撤回数、待处理数和导出资格的说明文案。
- [ ] 确认撤回后重新督办的 72 小时规则口径。
- [ ] 用无转办、一级转办、二级转办三类真实业务样例完成验收。

## 建议的业务方案

- 保持“提交即认可并上报”的现有规则。
- 在待上游提交节点增加「打回」，原因必填并退回直接下游。
- 督办人逐项提交产生「已审核/督办人已审核」。
- 督办人可以跳过逐项审核，直接导出全部有效记录均为已填报或已审核的批次。
- 导出成功后统一归档，作为本轮督办闭环的唯一批次级关闭动作。
- 当前批次选择范围同时决定事项卡合集和导出范围；任一选中批次不合格则整体禁止导出。
