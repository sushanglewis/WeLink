# PRD: 2026-09-07-supervision-gui-form

<!-- status: draft -->

> **背景与来源**：2026-09-07 业务方明确 IM 督办两大目标——(1) 基于 Teable 督办台账建设美观 GUI 看板（指标 + 列表 + 跟进记录下钻）；(2) 龙小督 agent 在 IM 聊内以消息表单方式推送填报任务，经办人逐条查看、填报、提交（一人可能有多项）。2026-09-08 PM 五轮决策回填（D-1~D-20；D-19/D-21 状态机与口径决策）；**D-20 聊内不做审核**——聊内弹窗=数据交互 GUI：督办人直接改数据+提交（保存 Teable）+导出 Excel（文件消息送达）+催办，无审核/打回/汇总页，提交存为填报消息可只读回看；D-18 交互模式立场见 `agent-vs-form-interaction.md`）。**2026-09-09 PM 决策 D-22 状态机双字段化（v0.6 修正）**：**状态1**（时间状态）单选 4 值（正常/风险/逾期/完结）+ **状态2**（跟进状态）单选 4 值（暂存/推进中/已填报/逾期未填报），两字段**完全独立**——状态1 仅按当前时间与截止时间计算（截止前 7 天=风险、过截止=逾期，与是否填报无关），**完结**由督办人在 Teable 手动修改（上级督办室线下同意，终态、不再被督办）；**去除「紧急」**（与业务风险定义冲突），其「超期未反馈/通知督办人跟进」职责归「推进中→逾期未填报」（过督办反馈 DDL，T3）；**延期**=督办人回改截止时间、状态1 按新锚点重置；导出 Excel 触发本轮关闭不变（D-21，T5）；D-19/D-21 被 D-22 取代，见 `state-machine.md` v0.6。上游需求：`issue-17/requirements/2026-08-24-issue-17/supervision-p0.md`（S-1~S-5）、`issue-17/designs/issue-17/feature-catalog.md`（F-F01/F-F02）、issue-6 Teable 集成。本文档对应 9/9 督办 V1 定稿评审材料之一。

## 产品目标

1. **督办看板 GUI（领导只读总览）**：面向领导/管理层，将 Teable「督办任务 + 跟进记录」以任务导向看板呈现——指标卡（D-22 双字段口径 7 张）、**筛选条件框可组合筛选**的事项列表、点击行下钻跟进记录时间线，GUI 无任何写操作入口。
2. **聊内逐条填报（含转办/润色/批量）**：经办人、转办人在 IM 内收到龙小督推送的表单卡片（iframe），以「第 k / 共 N 项」导航逐条填报五字段（落实/困难/下一步/预计完成时间/进度评价），支持**逐条提交、批量提交、转办（弹窗选人）、龙小督润色、暂存续填**（D-20 无申请办结/审核）。
3. **业务闭环**：任务下发唯一方式 = 督办人发送 Excel 给龙小督（解析校验→落主表〔状态2=暂存〕→督办人启动督办后通知经办人，下发即接收 D-13）；全部事项遵循双字段状态机（状态1 4 值 + 状态2 4 值，两字段完全独立，D-22/v0.6）；24h 填报监督；进入风险窗（截止前 7 天）/逾期未填报/逾期自动催办 = 原表单加急 + push 消息 + 加急可视化，不加新表单、无需人工点击（D-15）；逾期未填报同步通知督办人跟进（T3），逾期升级督办人（只读视图 + 催办手动入口 → IM+邮件）；填报闭环按双字段状态机（D-22+D-20）：提交→已填报（存为填报消息可回看）→督办人 DDL 查收（直接修改保存/导出 Excel/催办，无审核、无办结按钮）→**导出 Excel 后本轮关闭、已填报回暂存（D-21 触发不变，T5）**；完结=上级督办室线下同意后督办人在 Teable 手动将状态1 改为完结（终态、不再被督办），延期=督办人回改截止时间、状态1 按新锚点重置（D-22/v0.6）；转办链最多「经办人→转办人→次级转办人」三级；消息列表龙小督会话旁展示督办状态徽标（待填报事项数，区别于未读数，D-14）；批示过问本期不做（D-17）。
4. **数据闭环**：提交只写跟进记录表（创建人=实际填报人），主表反馈字段由 Teable 自动化同步；状态字段规范化单选；操作全量留痕。
5. **架构合规**：GUI 与表单统一走「Teable 数据底座 + 轻量 BFF 应用层」（路线B），share 链接不作为数据通道。

## 非功能需求

- **安全**：Teable Token 服务端托管、最小权限、可轮换；表单签名 URL 短时效一次性；iframe 白名单 + frame-ancestors + postMessage origin 校验；润色仅建议不落库直至确认；数据按身份隔离。
- **性能**：看板首屏 < 2s；表单预填 < 1s；iframe 高度自适应；组合筛选一次查询。
- **兼容性**：一期桌面端为主；二期移动端 WebView 直填；降级链接全端可用。
- **持久性**：表单草稿与批次状态服务端保存（D-12），客户端不依赖 localStorage；会话中断恢复不丢已填内容。
- **可维护**：Teable schema 变更仅 BFF 适配；状态值集/指标口径集中维护。
- **审计**：填报（创建人=填报人）、转办、催办、审批、改评全量留痕。

## 风险

- **邮箱催办通道 1.4.1 前未就绪**：D-4 要求 IM+邮箱 → 先 IM 即时发，邮件就绪后补渠道；BFF 通知层做渠道抽象。
- **状态历史数据清洗**：自由文本/原 6 值→双字段（状态1 4 值 + 状态2 4 值）的映射表需 PM 确认，清洗前备份防误归并。
- **Teable 自动化能力边界**：「取最新跟进记录同步主表」需 PoC 验证；不达标则回退「提交即回写主表」（BFF 双写+补偿）。状态机逻辑（T1/T2/DDL 判定、批次关闭推进）一律由 BFF/agent 驱动，不用 Teable 自动化硬编（D-18）。
- **进度评价字段现状为 formula**：值集已确认（推进中/已落实/已滞后，D-6/D-12），仍需字段改造（formula→单选）+改评留痕，影响现有公式依赖，实现期评估。
- **预警与督办 DDL 配置**：双字段独立判定后无串联约束；若批次督办DDL 晚于完成时限，「逾期未填报」（跟进字段）与「逾期」（预警字段）可并存于同一事项——展示口径实现期与业务确认。
- **Token 体系依赖 S-3**：用户 Token 托管未就绪将阻塞填报链路。
- **GUI 架构待研发评估**：范围不变，选型可能调整。
