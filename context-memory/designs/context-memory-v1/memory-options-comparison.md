## 推荐与对接设计（方案 A）

- **写入侧**：PG 消息表 → 不活跃检测（3h 无消息，`last_active_at` 扫描，阈值可配）→ 归档任务队列 → 轻量模型摘要 agent（选型见 feasibility，倾向小参数模型）→ 按规范 append/更新 `memory/users/{user_id}/matters/{matter_id}.md`。
- **读取侧**：混合触发（激活注入 / 信号检索 / 任务预载），读取接口为文件 + 索引清单，检索成本 O(目录列表)。
- **与 Teable 的边界**：账本只存协作背景与业务事实的引用键（事项 ID、批次 ID），不冗余台账字段。
- **审计**：账本目录纳入 git（或同等快照机制）；每次写入带 `source` 指针（会话/消息区间）可回查 PG 原文。

## 演进触发条件（何时重新评估 B/C）

同时满足以下两条即启动复评：
1. 活跃记忆条目（事项账本 + 摘要卡）持续增长超过单文件系统索引可舒适检索的量级（经验阈值：>5,000 个事项账本或检索 P95 > 2s）；
2. 出现明确的跨事项/跨人多跳关系查询需求（如「所有承诺依赖某供应商的事项」），文件+grep 方案确认无法满足。

复评优先顺序：先 mem0 自托管（接入快）做 PoC，Graphiti 作为关系推理确需时的候选。
